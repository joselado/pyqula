# The eighth sweep: ten areas read without running

On the morning of 15 November 2026, ten agents read ten areas of the package without running
any code. Each area was chosen by the files a repair would touch: the four modules of the
ultracell (`ultracelltk/`, `ultracell.py`, `htk/supercell.py`), the two mean-field engines
(`scftk/spinspin.py`, `scftk/densitydensity.py` and `densitydensity_kpm.py`), the couplings of
the classical models, the Kondo lattice, the KPM and response functions changed the day before,
and the builders that loop over a fixed box of cells. Each agent committed the repairs it was
sure of, with a test, and a second agent tried to refute every commit. 17 commits landed, from
b82a250 to 25c7047, four of them amended as the verifier asked. They round the supercell
matrix instead of truncating it, remove two copies and some temporaries of the ultracell
matrix, occupy the ultracell states with the smearing of the other engines, keep the
self-image pairs out of the Monte Carlo moves, read the onsite Kondo coupling of the selected
moments, fix the normalization of `kpm.dos` and the occupied states of `kpm.total_energy`, and
give the crystal field, a pairing of known range and the Kane-Mele and Haldane second
neighbors every cell within their range.

The two optimizations were timed after they landed, at two threads, on a machine with a load
of about 4, so the times are a ratio and not a reference. The ultracell matrix of spinful
graphene with Rashba coupling on 24x24 cells (2304 orbitals, 1420 kept states at `emax=1.0`)
is the same to the last bit, and the peak of its build goes from 9.1 to 7.5 matrices of the size
of the result; the build goes from 0.66 to 0.59 s, and the call with the eigenstates stays at
3.7 s, since the dense eigh dominates it. The spinful interaction of `Vinteraction_kpm` built
with `np.kron` is identical to the double loop, and on 576 sites and 7 directions it takes
0.09 s instead of 2.7 s.

What follows is what was found and left: the findings that the verifier also judged real. Each
entry gives the place, what is wrong and the concrete case. They were found by reading and none
was run. Some are repairs outside the files of their area, some need a decision of the
maintainer (an API choice, a default), and some are optimizations found by reading, which want
a timing before anything changes.

## Ultracell basis and matrix supercells

- `supercell.py:43` non_orthogonal_supercell (fill mode) searches candidate cells only in neighbor_cells(c) with c=|det M|, so a valid M whose entries are larger than |det M| loses atoms and h.get_supercell(M) or g.get_supercell(M) raises. Honeycomb, M=[[1,0,0],[2,1,0],[0,0,1]] (det 1, a2'=2a1+a2). The atom at x=+0.5 has fractional coordinates (1/6,-1/6). In the new cell its only image in the fill window is in cell R=(2,1), and the search covers only -1..1. One atom out of two is found, so ValueError 'not all the atoms of the supercell have been found ... increase ncheck', although ncheck is not used in fill mode. matrix_supercell claims to handle any M and inherits this. A strongly sheared M fails the same way: geometry.honeycomb_lattice().get_supercell([[1,0,0],[6,1,0],[0,0,1]]) needs the site at the primitive cell (5,1). The readers of two areas found this one independently.
- `hamiltonians.py:768` h.get_supercell routes only a 3x3 matrix to matrix_supercell. A 2x2 matrix for a 2D lattice goes to the repetition path and fails with an unrelated error. h=honeycomb; h.get_supercell([[2,1],[-1,1]]): normalize_nsuper pads it to [[2,1],[-1,1],1], and the geometry's np.array(nsuper) on this ragged list raises a numpy inhomogeneous-shape ValueError (or later n1*n2*n3 on lists raises TypeError). The error does not say that a 3x3 matrix is needed. It is an error, not a wrong result.
- `htk/supercell.py:45` matrix_supercell takes only sparse=, while the repetition path multicell.supercell_hamiltonian takes ncut= and passes other keywords to the geometry. The same keyword works for a vector nsuper and fails for a matrix. h.get_supercell([[2,1,0],[-1,1,0],[0,0,1]],ncut=5) raises TypeError: matrix_supercell() got an unexpected keyword argument 'ncut', while h.get_supercell([2,2],ncut=5) works. matrix_supercell has no range cut, so ncut has no meaning there.

## Ultracell matrix

- `ultracelltk/basis.py:303` An emax that keeps no state at any folded momentum of one kS raises ValueError, even when other kS of the mesh keep states. That ultracell has zero states there, so it should give no eigenvalues, not an error. Spinless honeycomb h, hs = h.get_supercell([2,2]), u = h.get_ultracell(hs, emax=-2.99), u.get_dos(nk=4). At kS=0 the folded momenta include Gamma (E=-3), so one state is kept. At kS=(0.25,0,0) the folded momenta are (0.125,0), (0.625,0), (0.125,0.5) and (0.625,0.5), all above -2.99 (for example -|2+exp(i pi/4)| = -2.80). So pad() raises 'no state of the unit cell is below emax, so the basis is empty' in the middle of the mesh. The same happens in counts() for a rebuilt basis.
- `ultracelltk/meanfield.py:92` MeshStates calls eigh(H) without overwrite_a, so the mean field still keeps H and a Fortran copy of it while eigh runs, three matrices with the eigenvectors. For every kpoint and iteration of u.get_mean_field_hamiltonian(), eigh copies the (kept)^2 matrix: 351 MB extra at 4684 kept states. H is not used after eigh, and since 92e70b0 it is in Fortran order. So eigh(H,overwrite_a=True), or calling matrix.eigenstates, would remove the copy and give the same values.
- `ultracelltk/observables.py:93` site_sum takes vs[:,keep] with a boolean mask, a full copy of the kept eigenvectors. For the LDOS the Lorentzian weight is never zero, so the copy is the whole (kept)^2 matrix. meanfield.occupied (line 133) does the same with the occupied states. u.get_ldos(...) at 4684 kept states holds vs (351 MB) plus vs[:,keep] (351 MB) per kpoint. Slicing vs by index per chunk (np.nonzero(keep) split by state_chunks) would avoid the copy and give identical numbers.
- `ultracelltk/basis.py:339` from_supercell keeps several chunk-sized temporaries alive at once: ph*Y, Z, the fftn output, and the division by sqrt(N) into a new array. Dividing in place would remove one of them. For a group of nb columns, about three or four arrays of norbs*nb complex numbers (up to 134 MB each at chunk_entries=2**23) are alive together inside the transform. This bounds the build peak for small ultracells, where it can be larger than the matrix itself.
- `ultracelltk/basis.py:347` basis_block recomputes folded_momenta(kS), an (N,3) array, for every momentum iq, so one ultracell matrix spends O(N^2) on recomputing the same momenta. For N cells, ultracell_matrix calls basis_block N times, and each call rebuilds all N folded momenta. By reading, this is a few percent of the build, and the build is itself small next to the dense eigh. It is not measured.

## Ultracell mean field

- `spectrum.py:494` At full (or empty) filling and finite T, the Fermi level that fermi_level() takes from get_fermi_energy_T is the T=0 cut plus (or minus) e_reg=1e-5 from filling.get_fermi_energy. The occupations in occupied() then use delta=T, so the top (or bottom) level is only about half occupied once T is well above 1e-5, and the density matrix does not hold the requested charge. Ultracell with every state kept (emax=None), filling=1.0, T=1e-2. fermi_level returns max(e)+1e-5, and the highest state gets 1/(1+exp(-1e-3)), about 0.50, instead of 1. So Tr(dm) is about n-0.5 instead of n. Filling 0 gives the mirror case, about 0.5 electron in the lowest state. integration="ed" does the same thing, so the two engines agree, and tests/ultracell/test_ultracell_meanfield.py::test_full_filling_without_a_cut checks only T=0.
- `ultracelltk/meanfield.py:192` SparseBackend runs the Fermi search at self.T, which is 0 for T=0 and also for T=None, while the occupations use delta=nonzero_smearing(T): 1e-15 for T=0, and delta_dm=1e-6 for T=None. The spinful "ed" path (full_dm_accumulate_sparse_with_fermi) searches at T=delta instead, and the spinless "ed" path searches at T. So at T=0 the ultracell follows the spinless convention. Pass T=0 explicitly with a level at the Fermi energy that is degenerate to below 1e-15 and that the filling splits unevenly, for instance 1 of 3 states needed. The T=0 midpoint gives about 1/2 to each degenerate state, which puts the charge 0.5 off. The spinful "ed" search at T=1e-15 would try to give 1/3 each. With T=None, which no current caller passes, the search is at T=0 and the occupations at 1e-6.
- `ultracelltk/meanfield.py:155` Possible optimization, not done: the union of pairs in dm_entries holds both (i,j), from the entry at d, and (j,i), from the Fock entry at -d. At one kpoint S[j,i]=conj(S[i,j]), so about half of the pair_sums work could be taken by conjugation. Cost argument: pair_sums does O(npairs*nocc) work per kpoint, and roughly half of the pairs are transposes of the other half, so up to 2x on that kernel. The roadmap timing (future_development/ultra_long_range.md) puts the dense eigh of the ultracell matrix at 19 of 24 s at 2716 kept states. The pair sums are a part of the remaining 5 s, so the total gain is small and has not been measured.
- `ultracelltk/meanfield.py:133` Possible optimization, not done: occupied() takes states.vs[ik][:,keep] with a boolean mask, which copies the occupied columns. The eigenvalues from eigh are sorted, so keep is a prefix and a slice [:, :nocc] would be a view. Cost argument: this saves one copy of (nkept x nocc) complex numbers per kpoint and iteration. That is memory and bandwidth only, small next to the O(nkept^3) eigh, and real_space_states copies the coefficients again into C anyway.

## Ultracell observables

- `ultracelltk/observables.py:77` For a non-diagonal supercell matrix, the default delta of u.get_dos() takes min(nk*n) over the entries n of the diagonal form, and this does not measure how dense the folded mesh is. Take the sqrt3 x sqrt3 (Kekule) cell M=[[2,1,0],[-1,1,0],[0,0,1]]. Its diagonal form gives n=(1,3), so u.get_dos(nk=10) uses delta=5/10=0.5. The folded momenta are 300 points of the unit-cell zone, about 17 per direction, where dos_kmesh would take about 0.29. So the default broadening is about twice too large. The docstring says 'the width h.get_dos() would use on the mesh of the unit cell that the folded momenta form', and that mesh is not rectangular here.
- `ultracelltk/observables.py:140` The guard of u.get_vev() only checks emax>0 against the clean unit cell. With a lattice-periodic shift in hs, occupied states can be outside the basis and no error is raised. Take hs = supercell of h plus a uniform onsite -1, and build u=h.get_ultracell(hs,emax=0.5), with or without rebuild_basis (the rebuilt basis keeps as many states as the clean cut). Then the clean states with energy between 0.5 and 1 are occupied in hs, because their hs energy is below zero, but they are not in the basis. u.get_vev() returns occupations that are too small, without error. The mean-field loop is protected by meanfield.fermi_level, which raises when the filling needs more states than kept, but this direct call is not.

## The VJinteraction engine

- `ultracelltk/meanfield.py:217` With a fixed chemical potential, the ultracell backend of VJinteraction never checks that mu lies below the highest kept state. With a filling, fermi_level raises in that case ("build it with a larger emax"). spinspin's ultracell branch (h.shift_fermi(-mu); ultracell.dm(h, sparse_needed)) and band_energy(h) then treat the states cut away above emax as empty, even when they lie below mu. Take graphene, hs = h.get_supercell([3,2]) and u = h.get_ultracell(hs, emax=0.5). Then u.get_mean_field_hamiltonian(U=1.0, mu=1.0) runs. The clean-cell states between 0.5 and 1.0 are not in the basis, so their occupation is silently left out of the density matrix, the mean field and the band energy, and the loop converges to a wrong state. The same cut at a filling that puts the Fermi level above the kept states raises ValueError. The spinless loop (densitydensity._ultracell_sparse_loop to Vinteraction_kpm with backend=) takes the same SparseBackend.dm path.
- `scftk/spinspin.py:1037` VJinteraction accepts the KPM-only keywords (scale, npol, ne, cores, kpm_prec, kpm_radius) with integration="ed" or "ultracell" and ignores them without a message. The use_jax=True branch refuses the same keywords as "must not be silently ignored". u.get_mean_field_hamiltonian(U=2., filling=0.5, npol=400) or h.get_mean_field_hamiltonian(U=2., npol=400) (integration="ed") runs and returns the ED or ultracell result. Nothing tells the caller that npol had no effect.
- `scftk/spinspin.py:84` _build_v and _build_density_v fill each (2n,2n) spin-orbital matrix with a pure-Python double loop over site pairs, once per bond direction and per channel (four calls per dense VJinteraction). np.kron(m, pattern) with pattern [[1,-1],[-1,1]]/4 or ones((2,2)) gives the same entries, exact because the factors are powers of two. Cost argument: there are n^2 Python iterations with 4 numpy scalar writes each, per direction and per channel. A 200-site supercell with J1 in 2D has about 9 directions times 4 channels, which is about 1.4e6 loop iterations before the SCF starts. A kron call does the same work in milliseconds.

## The density-density engines

- `scftk/densitydensity_kpm.py:195` When a backend (the ultracell SparseBackend) is used, the KPM-only keywords npol, scale, ne, cores, kpm_prec and kpm_radius are still accepted as named parameters of densitydensity_kpm and generic_densitydensity_kpm, but nothing uses them, and no error is raised. For a spinless ultracell, u.get_mean_field_hamiltonian(V1=1.5, filling=0.5, kpm_radius=3) or npol=50 runs with the exact ultracell states and silently ignores the keyword. The spinful route (spinspin.VJinteraction with integration="ultracell") also takes these as named parameters and refuses them only under use_jax=True (spinspin.py around line 669), so the two routes behave the same way.
- `scftk/densitydensity_kpm.py:84` The sparse loop does not convert a dense starting mean field to csr. If one comes in, the loop computes on dense matrices from then on, and its convergence measure changes. First run a dense Vinteraction, which writes MF.pkl by default. Then, in the same directory, run Vinteraction_kpm on a sparse h of the same shape with the default load_mf=True. mf_matches_hamiltonian checks only the shape, so the dense MF.pkl is accepted. A dense mf= dictionary passed directly has the same effect. update_hamiltonian then adds a csc matrix to an ndarray, which gives an np.matrix while h.is_sparse stays True. mix_mf keeps the mean field dense on every iteration, and diff_mf, which no longer sees sparse matrices on both sides, takes the mean over all n^2 entries instead of the mean per stored entry. This weakens maxerror by about nnz/n^2. The ultracell tests convert their dense guesses to csr by hand for this reason.

## Couplings of the classical models

- `classicalspintk/localenergy.py:20` The classical spin local energy halves a pair (i,i) as well, so the local energies do not sum to the total energy when a site couples to its own periodic images. The Ising and gas local energies count that pair fully. SpinModel on geometry.triangular_lattice().get_supercell(2) with add_heisenberg(Jij=[1.,0.5,0.2]) has J_ii=1.2 on each of the 4 sites. For unit spins, sum(get_local_energy()) is 2.4 below energy().
- `specialhopping.py:410` A HoppingGenerator coupling is cut at rcut=5.0 by default in a periodic system, while a list of shells keeps the range of its shells. The two disagree for a shell beyond 5. On geometry.chain(), add_interaction(Jij=NNG(g,[0,0,0,0,0,0.7])) gives no coupling and zero energy, while Jij=[0,0,0,0,0,0.7] gives a coupling of magnitude 1.4.
- `specialhopping.py:400` folded_interaction keeps the onsite value Jij(r_i,r_i) of a function coupling (distance_cut_interaction with onsite=True), while latticegas.add_tensor skips self pairs. add_interaction(Jij=lambda r1,r2: np.exp(-np.linalg.norm(r1-r2))) adds J(0)=1 on every diagonal. In the gas this acts as a chemical-potential shift J(0)*n_i. With an anisotropic Jm it is a single-ion anisotropy in the spin model. A 1/r tail raises instead of being taken between different sites only.
- `multicell.py:360` parametric_hopping_hamiltonian drops a whole cell direction when sum|m| <= 1e-5, before distance_cut_interaction applies its rcut cut. The threshold is absolute. A weak coupling, for example Vr = 1e-7*exp(-d), keeps its pairs inside cell 0 but loses all pairs to the images. The cell-versus-supercell invariance then breaks at that level.
- `specialhopping.py:398` The HoppingGenerator path of folded_interaction has no reality or reciprocity check (require_pair_interaction), and the classical models keep only .real, so an imaginary part is dropped silently. A generator with complex entries, for example a phase times NNG, gives a coupling made of its real part only, with no error. The same coupling written as a function raises 'Jij must be real'.
- `specialhopping.py:306` shell_interaction calls g.neighbor_distances() with its default n=4 and truncates vs to len(nd), so a fifth or later shell would be dropped silently. shell_interaction(g,[V1,V2,V3,V4,V5]) drops V5. Every current caller passes three shells, so the bug is latent only.
- `latticegas.py:469` get_local_mu includes J_ii*den_i for a self-image pair, although its docstring says the result does not depend on the site's own occupation. On the 2x2 triangular cell with [1.,0.5,0.2], get_local_mu()[i] changes by J_ii=1.2 when den[i] goes from 0 to 1.

## Kondo lattice

- `scftk/kondolattice.py:361` The Kondo loop does not store h.temperature (or h.nk) on the converged Hamiltonian. Since feec2ff the other loops (densitydensity, spinspin, KPM, jax) all do, so that observables read the occupations at the loop's T. Take the chain with J=1.5, filling=0.15, T=0.02 (the default T). h2.local_occupation is 1 to 1e-8 at T=0.02. h2.temperature stays 0.0, so h2.get_density_matrix(), get_vev, get_magnetization and get_filling read at delta_dm=1e-6 (default_smearing), and the f occupation read from h2 is not exactly the constrained 1.
- `scftk/kondolattice.py:411` total_energy mixes a T=0 band energy with an electron count at T. h.get_total_energy sums the eigenvalues below zero (a step), while n_electrons = trace(dm) is taken with the smearing T. At fixed mu and T=0.02, the reported energy is sum_{e<0} e + mu*N_T. The T=0 energy would be sum_{e<0} e + mu*N_0, and the grand potential would be -T sum ln(1+e^{-e/T}) + constants. It is neither. Two branches (V=0 and V!=0) compared at the same mu differ in N, so the comparison carries an O(T) error in mu*(N_T - N_0). The stationarity tests use the grand potential they compute by hand, not scf.total_energy.
- `scftk/kondolattice.py:310` Optimization by reading: each iteration builds the full n x n density matrix for every bond direction -R. full_dm_accumulate does one n^3 matmul per k-point per direction, while the loop needs only two elements per bond and the (0,0,0) diagonal. On a square lattice with J(rc, rm) nonzero up to the default rcut=5, the bonds reach about 81 directions. One iteration then costs about 81 times the density matrix of the onsite model. This cost argument is not measured.
- `scftk/kondolattice.py:356` The V residual is now relative to the largest field of all bonds and all moments. So with several moments and a number J, the commit's claim 'bit for bit as before' holds only for one moment per cell. A small but genuine field converges only to an absolute tolerance maxerror*max|V|. Take an inhomogeneous supercell with a number J, where one moment has V of about 1e-3 and the others about 0.3, with maxerror=1e-5. The loop stops once the small V moves by less than 3e-6, which is a relative error of about 3e-3 on that field. Before, it was converged relative to its own size.

## KPM and response functions

- `conductivitytk/kpmkubo.py:517` At T=0, absorptive() samples the occupation factor [f(E)-f(E+w)]/w, a box of width w, on Chebyshev-Gauss nodes spaced about pi*a/ne, which is roughly delta/7 at the default ne=4M. Below that spacing the box holds zero or one node, so the Drude part of a metal at small w is either 0 or several times too large. reactive_part() samples absorptive() from delta/16 upward, so the error also enters the Kramers-Kronig transform. Take a clean metallic chain with integration='kpm', T=0 and the Fermi level in the band. Re sigma_xx(w) at w = delta/16 to about delta/4 jumps between 0 and several times the Lorentzian Drude value, depending on where the nodes fall relative to the Fermi level. The reactive part inherits a few-percent error. The default T=delta hides it.
- `bsetk/interaction.py:340` density_interaction fills the spinful 2x2 blocks with a Python double loop over the sites, once for every lattice vector. Since 8e904ac shell_interaction can return more cells, so the loop runs more often. Commit ef2d06a replaced the same loop in Vinteraction with np.kron(m, np.ones((2,2))), which gives the identical matrix. For a BSE interaction on a cell of several hundred sites, the loop runs n_cells*ns^2 Python slice assignments, which by the ef2d06a measurement is of order seconds.
- `conductivity.py:1145` The optical_conductivity dispatcher forwards *args to two signatures that differ from the fifth positional argument on. In the band path the fifth is intraband, in kpmkubo.optical_conductivity it is component. conductivity.optical_conductivity(h,ws,1,0.05,0.1,False,integration='kpm') passes False as component, where the same call with integration='grid' takes it as intraband=False.
- `spectrum.py:339` The use_kpm=True path of spectrum.total_energy never passes fermi to kpm.total_energy, so the KPM energy is always the one at fermi=0. total_energy(h,use_kpm=True,fermi=0.5) returns the energy of the states below 0, while the diagonalization path sums the states below 0.5.
- `conductivitytk/kpmkubo.py:652` _imaginary_resolvent allocates a buffer of nb=32 Chebyshev vectors of size n*nc outside the memory= budget. Only the per-energy accumulator Y is sized by memory. With n = 1e6 orbitals and nd=2 (nc=3 for a stochastic vector), the buffer is 32*3e6*16 bytes, about 1.5 GB on top of the 2 GB budget of singleshot.

## Loops over a fixed box of cells

- `superconductivity.py:390` A pairing given as a callable mode has no known range (df.rcut is None), so add_pairing and check_fermi_antisymmetry (sctk/pairing.py:122) still visit only the box of neighbor_directions(), geometry.ncells=2. On geometry.chain(), add_pairing(mode=f) with f(r1,r2) = identity(2) when |r1-r2|=3, else zero. That is a third-neighbor singlet given as a function, and it adds no pairing, without a warning.
- `kanemele.py:268` The single-cell storage of add_kane_mele and add_haldane_like (intra, inter, tx, ty, txy, txmy, intermediate sites from the cells -1..1) cannot hold a second neighbor beyond the 9 cells, so on a non-reduced 2D cell the bonds are lost. A non-multicell 2D Hamiltonian on a cell with a2' = a2 + 2*a1, where the honeycomb second neighbor a2 sits in the cell (-2,1): add_kane_mele and add_haldane drop it. The multicell path is complete after b3e6954.
- `kanemele.py:134` km_vector_jit returns the cross product of the first intermediate site it finds. On lattices where one second neighbor has two paths with opposite orientation, the sign depends on the KD-tree order of find_close_neighbors_batch. On geometry.triangular_lattice() with add_kane_mele or add_haldane, the pair at distance sqrt(3) has two common first neighbors with opposite cross products. The coupling picks one of them by KD-tree order, so it can change with the number of candidate sites, for instance between the unit cell and a supercell.
- `meanfield.py:495` coulomb_interaction and fast_coulomb_interaction set g.ncells = max(int(2*rcut/|a1|),1) on the caller's geometry, which is a box set only by a1 that also mutates the geometry. They also call g.replicas(d) positionally, but Geometry.replicas takes keywords only, so both raise TypeError at the first cell. meanfield.coulomb_interaction(geometry.honeycomb_lattice()) raises TypeError from replicas(d). The only caller, scftypes.scfclass.setup_interaction(mode='Coulomb'), is never called in src/ (its call sites are commented out).
- `kanemele.py:377` add_kane_mele_old keeps a box of ncells=4 and adds Kane-Mele only to the hoppings that already exist, the bug that add_kane_mele fixed long ago. A first-neighbor diamond Hamiltonian with add_kane_mele_old misses the second neighbors in the six cells it has no hopping to.
- `sctk/fastdeltaud.py:23` hopping2deltaud builds each pairing block with a Python double loop over n x n site pairs, dense t matrices and an n x n bmat of blocks, so it is O(n^2) per direction although the docstring says it can be fast for very large systems. For a 2000-site cell this is 4e6 Python iterations and a 2000 x 2000 Python list of blocks per lattice direction. A coo construction from np.nonzero of (|mud|>=1e-6)|(|mdu|>=1e-6) gives the same values.
